# MEM-02 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox syntax for tracking.

**Goal:** Просмотр памяти без модели и управление её подключением в Telegram и desktop.
**Architecture:** Общий безопасный read-only API hub-memory; единый путь сохранения
настройки через supervisor; два интерфейса поверх общих операций. Подключение
агента фиксируется при запуске процесса, независимо от последующих переключений.
**Tech Stack:** Rust 1.96, Tokio, egui, teloxide, существующий JSON Store.
**Spec:** ../specs/2026-11-15-memory-management-design.md — утверждён пользователем.

## Global Constraints

- Оба интерфейса входят в этап. Глобальная настройка по умолчанию true.
- Выключение сохраняет данные; применяется только к новым процессам, включая resume.
- Просмотр не создаёт хранилище. Формат и гарантии записи сохраняются.
- 500 ключей, 32 ревизии/ключ, 8 МиБ; лимиты MCP search остаются 1–20.
- Самостоятельные CLI, сторонние MCP и модели не изменяются.
- Без commit/push/релиза. Существующие незакоммиченные документы сохранить.

## Review Focus

- Пустая область, unsafe path и повреждение не должны превращаться в пустой успешный результат (task 1).
- Два интерфейса и несохранённая форма не должны терять изменения настройки (task 3).
- Живой процесс сохраняет старое подключение; resume получает новое (task 2).
- Старые кнопки после смены cwd не читают старую область (task 4).
- Длинный Unicode-текст и устаревший GUI-ответ не скрывают данные и не меняют проект (tasks 4–5).

## Карта изменений

hub-memory: store.rs и новый inspection.rs, exports в lib.rs; тесты storage/behavior.rs.
hub-core: settings.rs, commands.rs и соседние тесты в исходных модулях.
hub-telegram: новый memory.rs, hub.rs, agents.rs, session.rs, lib.rs, Cargo.toml.
hub-app: supervisor.rs, connector.rs, config.rs при необходимости сериализации,
новый memory.rs; GUI memory.rs, app.rs, settings.rs, mod.rs.
Backend-крейты: существующие protocol/outgoing/backend-тесты подключения памяти;
product-код менять только при доказанном нарушении disabled/resume-контракта.

### Task 1: Общий просмотр без создания хранилища

**Interfaces:** экспортировать `MemoryReader::new(base: &Path, project: &Path)
-> Result<MemoryReader, Error>`, `inspect(&self, query: &str, offset: usize,
limit: usize) -> Result<MemoryPage, Error>`, `get(&self, key: &str,
revision: Option<u32>) -> Result<Entry, Error>`.
`MemoryPage`: канонический project, directory, exists, bytes, key_count,
matched_count, entries: Vec<SearchHit>. Ревизии 1..=latest.revision доступны
через get; чтение каждой страницы проверяет существующий формат и область.

- [ ] Добавить тесты: отсутствующая область не создаёт ни base, ни lock/data;
  existing store виден reader; чужая область/unsafe path/corruption дают ошибки;
  поиск по ключу находит запись, страницы не теряют ключи при одинаковых timestamp;
  исторические ревизии и статистика соответствуют сохранённым байтам.
- [ ] Запустить `cargo test -p hub-memory`, подтвердить красные новые тесты.
- [ ] Выделить повторно используемый валидируемый путь чтения из store.rs;
  не обходить существующую защиту файловой системы через прямой fs::read.
  Пустой результат возвращать только для действительно отсутствующих данных.
- [ ] Добавить key в поисковый текст существующего Store::search и reader,
  сохранив семантику all terms, порядок и MCP-лимиты. Пагинация reader — 20 записей.
- [ ] Повторить `cargo test -p hub-memory`, включая существующие protocol/storage тесты.

### Task 2: Настройка и состояние процессов

**Interfaces:** `MemorySettings { enabled: bool }`, Default=true;
поле memory в Settings/Draft/SettingsFile. Состояние активного подключения
`MemoryConnection::{Enabled, Disabled, Unknown}` публиковать вместе с TopicView.
Enabled означает конфигурацию запущенного процесса, не успешность каждого MCP-вызова.

- [ ] Добавить тесты старого TOML без memory, false roundtrip и Draft roundtrip;
  флаг не влияет на Telegram-настройки и не требует restart бота.
- [ ] Добавить тесты выбора MemoryMcp по зафиксированному снимку настроек:
  смена флага не меняет живой процесс, следующий запуск получает новое значение.
- [ ] Запустить `cargo test -p hub-core -p hub-telegram`, получить ожидаемые failures.
- [ ] Протянуть флаг через HubAgents::memory и публикацию фактического состояния;
  не читать новый watch-снимок отдельно от остальных настроек того же запуска.
- [ ] Расширить тесты всех пяти бэкендов: enabled → disabled → enabled,
  new и resume, сторонние MCP сохранены; handoff не подключает встроенную память.
- [ ] Запустить `cargo test -p hub-core -p hub-agent -p hub-telegram -p hub-claude -p hub-codex -p hub-qwen -p hub-hermes -p hub-opencode`.

### Task 3: Общий путь переключения и асинхронное чтение

**Interfaces:** типизированный запрос `SetMemoryEnabled { enabled, expected_revision,
reply }`; ответ успешен только после сохранения. expected_revision сверяется
с текущим save_revision. Во время другого save вернуть Busy, не терять запрос молча.
Порт из hub-telegram в app — mpsc/oneshot, без зависимости telegram от app.
Read-only операции выполняются spawn_blocking с ограниченным числом задач;
ответы GUI несут generation выбранного проекта/запроса.

- [ ] Тесты supervisor: переключение меняет только memory, ошибки записи
  не применяют флаг, stale revision отклоняется, активная задача не прерывается.
- [ ] Тесты SettingsForm: внешнее изменение memory сливается при неизменённом
  локальном поле; если поле также редактировалось, явный конфликт блокирует
  сохранение до выбора значения; остальные локальные поля сохраняются.
- [ ] Запустить `cargo test -p hub-app`, подтвердить новые failures.
- [ ] Добавить порт управления, связать connector и supervisor; использовать
  существующий store.save и finish_save, не создавать второй writer настроек.
  Неполностью настроенное приложение может просматривать память; переключатель
  до валидного первого сохранения недоступен с объяснением.
- [ ] Реализовать merge/conflict формы и асинхронную модель чтения с generation.
- [ ] Повторить `cargo test -p hub-app`.

### Task 4: Telegram /memory

**Interfaces:** Command::Memory; MemoryController обслуживает menu/search/get,
callbacks и настройку через порт task 3. Область берётся из актуальной темы,
не из присланного пользователем пути. Вызов доступен при работающем агенте.

- [ ] Тесты команды: /memory, /memory search QUERY, /memory get KEY [REVISION],
  неверные аргументы; проверка действующего allowlist до чтения и переключения.
- [ ] Тесты меню/карточки: пустая область, ошибки, 20+ записей, Unicode-текст
  длиннее Telegram-лимита, источники/история; key не исполняется как разметка.
- [ ] Тесты callbacks: другая тема/пользователь/сменившийся cwd отклоняются;
  переключение требует отдельного подтверждения глобального действия.
- [ ] Запустить `cargo test -p hub-core -p hub-telegram`, получить failures.
- [ ] Реализовать controller и маршруты до очереди задач агента; bounded callbacks
  содержат непрозрачный ID, состояние проверяет текущую тему и пользователя.
  Страницы длинного текста сохраняют весь контент и валидные Unicode-границы.
- [ ] Повторить тесты; обновить меню команд и help из общего реестра.

Уточнения реализации:

- Reader размещён рядом с Store, чтобы повторно использовать приватные
  проверки формата и безопасного файлового доступа. Новый формат не вводится.
- Длинная запись Telegram выдаётся полностью несколькими сообщениями через
  существующий механизм разделения; список записей имеет кнопки пагинации.
- Подключение активного процесса представлено Option<bool>: None означает
  отсутствие данных, а не выключенную память. Это конфигурация процесса,
  не доказательство успешности каждого вызова MCP.
- Для одного булевого поля нет третьего конфликтующего значения: при
  изменении с одной базы обе стороны выбирают одно и то же новое значение.
  Внешнее значение сливается, если поле локально не менялось; прочие правки
  формы сохраняются. Сохранение переключателя использует save_revision.
- Новые reader/settings/GUI-merge тесты наблюдались падающими до реализации.
  Часть остальных тестов добавлена после реализации; весь этап не заявляется
  как выполненный строго test-first. Финальные четыре regression-теста
  отдельно проверены на ошибочном поведении и после исправления.
- Работа велась в текущей ветке с сохранением незакоммиченных материалов MEM-01;
  отдельный worktree не создавался. Изменения не изолированы от этого checkout.

Не выполнено: интерактивная приёмка окна и Telegram, новые живые модельные
проверки enabled → disabled → enabled для всех пяти CLI, запуск Windows/macOS.
Существующие автоматические new/resume/MCP тесты прошли; это не заменяет
проверку реальных клиентских процессов. Модельные запросы не запускались.

### Обратная связь ручной проверки

Пользователь подтвердил, что нашёл запись и в GUI, и в Telegram.
При запросе mem01-pilot-quick-check@5 GUI показывал техническое
`revision Some(5) was not found` и безусловное предупреждение об устаревании.
Проверены только метаданные локальной записи: существуют ревизии 1, 2, 3, 4.

Исправление: общие сообщения просмотра локализованы; для отсутствующей ревизии
показываются доступный диапазон и способ открыть последнюю. Отсутствующий ключ
отличается от отсутствующей ревизии. GUI сообщает о сохранённом предыдущем
результате только если он действительно показан; при изменении ключа ревизия
сбрасывается на последнюю. Новый интеграционный тест воспроизвёл исходную
ошибку (RED) и прошёл после исправления (GREEN).
Подтверждение базового поиска не заменяет оставшиеся проверки переключателя
и поведения реальных процессов; их статус пока не изменён.

Первый запуск вкладки: пользователь нажал «Открыть» без выбранного проекта;
воспроизведено чтение пустого пути вместо проверки ввода. Исправлено:
поиск недоступен до выбора каталога, «Открыть запись» — до ввода ключа;
видна подсказка о порядке действий. Защита в load не запускает файловый поток
при незаполненном каталоге/ключе. Два регрессионных теста сначала упали на
исходном поведении; последующая проверка выполняется на исправленной сборке.
