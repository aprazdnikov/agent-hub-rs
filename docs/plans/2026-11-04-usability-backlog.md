## Цель и исходные данные

Управлять работой агентов с телефона без возвращения к компьютеру, понимать состояние
задач и получать результаты после сбоев связи.

Подтверждено пользователем:

- Возвращаться к ПК приходилось, когда забывал включить VPN.
- Без VPN недоступны ресурсы проектов; Telegram и агенты доступны.
- Используется несколько VPN, среди них OpenVPN и реализация snx на Rust.

Нужно уточнить: ОС рабочего ПК, точную реализацию и версию snx, способ запуска обоих
клиентов, требования к правам и интерактивной авторизации. Наличие Linux в рабочем
окружении разработки не считаем подтверждением ОС всех целевых компьютеров.

## Техническая основа и ограничения

Проект использует Rust, Tokio, egui и teloxide. Чистые типы и правила находятся в
`hub-core`, системная интеграция и GUI — в `hub-app`, команды Telegram — в
`hub-telegram`, общие контракты агентов — в `hub-agent`.

Для ближайших сценариев VPN используются универсальные пользовательские действия.
Специализированные профили и интеграции OpenVPN/snx ниже сохранены как отложенные идеи;
собственный VPN-протокол не нужен. Команды незавершённых задач — предложения,
а не существующий API.

- Подключение VPN должно работать независимо от доступности модели агента.
- Команды запуска задаются локально; сообщения Telegram выбирают сохранённый профиль,
  но не формируют произвольную shell-команду.
- Состояние VPN и доступность конкретного ресурса показываются отдельно.
- Подключение одного профиля не должно молча отключать другой. Правила совместной работы
  определяются после проверки клиентов, маршрутов и DNS.
- Пароли, ключи и токены не передаются в Telegram и не записываются в открытые настройки
  или логи. По возможности авторизация остаётся в существующем VPN-клиенте.
- Обычный запуск агента не должен зависеть от наличия настроенных VPN-профилей.
- Перенос контекста между агентами — передача сводки, а не совместимость их session_id.
- Изменения настроек и хранилищ должны сохранять чтение существующих пользовательских данных.

Не входит в этот backlog: собственный VPN-клиент, автоматическая смена маршрутов без
настройки пользователя, веб-панель, новые агентные бэкенды, управление несколькими ПК.

## Задачи

### AH-01. Проверить управление установленными VPN-клиентами

Результат: короткое техническое решение с проверенными способами определения состояния,
подключения и отключения каждого клиента.

Критерии готовности:

- Зафиксированы ОС, точные клиенты/версии и наличие CLI, API или системного сервиса.
- Для каждого клиента проверены уже активное подключение, успешный запуск, неверная
  авторизация, недоступный сервер, тайм-аут и необходимость интерактивного ввода/MFA.
- Определено, кто управляет процессом и правами: хаб, клиент или системный сервис.
- Проверено, могут ли два профиля работать одновременно; описаны ограничения маршрутов/DNS.
- Если полностью удалённое подключение невозможно, явно описан оставшийся ручной шаг.

Проверка: ручной сценарий на целевом ПК с согласованным тестовым ресурсом. Реальные
переключения соединений проводить отдельно от исследования, учитывая текущие задачи.
На этой стадии не угадывать команды snx по названию проекта.

### AH-02. Общие VPN-профили и выполнение локальных действий

Результат: пользователь сохраняет несколько именованных VPN-профилей и управляет ими
через общий сервис приложения.

Критерии готовности:

- Профиль содержит стабильный ID, отображаемое имя, тип интеграции и её настройки.
- Доступны состояния «отключён», «подключается», «подключён», «отключается», «ошибка»,
  «неизвестно»; живой процесс сам по себе не доказывает успешного подключения.
- Повторное нажатие не запускает второй процесс; операции имеют конечное время ожидания.
- После перезапуска хаб определяет фактическое состояние, а не доверяет старому флагу.
- Ошибка одного профиля не останавливает бота и остальные профили.
- Настройки валидируются локально, секреты не попадают в вывод и логи.

Опорные файлы: `crates/hub-core/src/settings.rs`, `crates/hub-app/src/config.rs`,
`crates/hub-app/src/supervisor.rs`, `crates/hub-app/src/gui/settings.rs`,
`crates/hub-app/src/secrets.rs`. Расположение нового VPN-модуля определить после AH-01.

Проверка: fake-клиент для переходов состояний, ошибок, тайм-аутов и повторных операций;
`cargo test -p hub-core -p hub-app --locked` — PASS.

### AH-03. Интеграция OpenVPN

Результат: выбранный установленный клиент OpenVPN работает через профиль хаба.

Критерии готовности:

- Поддержан проверенный в AH-01 способ управления существующей конфигурацией.
- Корректно определяются соединение, отказ авторизации, отключение и уже запущенный клиент.
- Выход из хаба не отключает чужое/ранее запущенное соединение без явно выбранной политики.
- Документированы требуемые права и поддержанные ОС/варианты клиента.

Опора: интерфейс AH-02; точные файлы интеграции определяются в плане этой задачи.
Проверка: контрактные тесты на fake-клиенте — PASS; вручную подключить тестовый профиль,
проверить ресурс и отключить именно его, не затрагивая второй VPN.

### AH-04. Интеграция snx на Rust

Результат: конкретная пользовательская реализация snx работает через тот же интерфейс.

Критерии готовности:

- Интеграция опирается на проверенную версию и её фактические команды/API.
- Поддержаны состояние, подключение, отключение и объяснимые ошибки.
- Сценарий с MFA/интерактивным входом либо реализован выбранным способом, либо явно

- Проверена совместная работа с OpenVPN либо показана конкретная несовместимость.

Опора: интерфейс AH-02; точные файлы определяются после идентификации проекта snx.

реального ресурса. Проверки двух VPN не должны менять рабочие соединения незаметно.

### AH-05. Управление VPN из Telegram

Результат: предложенная команда `/vpn` показывает профили и кнопки действий.

Критерии готовности:

- Видны имя и состояние каждого профиля, доступны подключение, отключение и обновление.
- Операция выполняется без запуска LLM; отказ агента не мешает управлению VPN.
- Действуют существующие chat/user allowlist; устаревшие кнопки не запускают новые операции.
- Повторное нажатие показывает текущую операцию. Успех и ошибка отражаются в карточке.
- Отключение требует подтверждения с именем выбранного профиля.

Опорные файлы: `crates/hub-core/src/commands.rs`, `crates/hub-telegram/src/hub.rs`,

`crates/hub-telegram/src/menu.rs`; связь с сервисом AH-02 через контракты приложения.

Проверка: fake-сервис, запрещённый пользователь, двойной callback, ошибка и тайм-аут;

### AH-07. Проверка ресурсов проекта: `/doctor`

Результат: пользователь видит готовность текущего проекта без обращения к агенту.

Критерии готовности:

- В профиле задаются проверяемые ресурсы и явное условие успешной проверки; список
  протоколов первой версии выбрать при детализации, не включать всё сразу.
- Карточка отдельно показывает наличие каталога/CLI, состояния нужных VPN и доступность
  ресурсов, с временем последней проверки. Наличие CLI не означает проверку авторизации.
- Проверки имеют тайм-ауты; не требуют платного обращения к модели.
- Недоступность сервера не объявляется доказательством отключённого VPN.
- Доступны повторная проверка и переход к подключению нужного профиля через AH-05.
- После подключения выполняется новая проверка; задача агента автоматически не повторяется.

`crates/hub-telegram/src/hub.rs`; профили AH-06.

Проверка: локальные тестовые endpoints, успешный ответ, неверный ответ и тайм-аут;

### AH-08. Модель и режим работы на уровне темы

### AH-11. Сохранение последнего результата и `/last`

Результат: итог завершённого хода можно повторно получить после сбоя отправки или перезапуска.

Критерии готовности:

- При детализации определено, какие текстовые блоки считаются итогом для каждого бэкенда.
- Текст результата привязан к теме и идентификатору запуска и сохраняется до отправки.
- `/last` возвращает результат текущей темы либо объясняет его отсутствие.
- Повторное получение не запускает агента. Ошибка записи на диск видна пользователю.
- Определены срок/объём хранения и права доступа. В первой версии не обещается повторная
  отправка файлов, которые могли быть удалены или изменены после завершения.

Опорные файлы: `crates/hub-telegram/src/session.rs`, `crates/hub-telegram/src/hub.rs`,

### AH-12. Очередь недоставленных результатов

Результат: сохранённые текстовые итоги доставляются после восстановления Telegram.

Критерии готовности:

- Учтена неопределённость «Telegram принял сообщение, ответ потерян»: exactly-once не
  обещается; повторный итог содержит понятную привязку к задаче.

### AH-17. Передача задачи другому агенту со сводкой

Результат: пользователь продолжает задачу другим агентом без ручного пересказа.

Критерии готовности:

- Сводка содержит цель, выполненное, важные решения, затронутые файлы и следующие шаги.

- Получатель стартует новую сессию с этим текстом, а не получает чужой session_id.
- При ошибке подготовки/запуска исходная сессия остаётся доступна.
- Выполняющийся ход не обрывается молча; не обещается перенос скрытого контекста,

выполняется отдельно, поскольку может расходовать токены.

## Правила детализации и проверки

- До реализации задачи закрыть её вопросы проектирования; затем записать небольшой
  исполнимый план с точными новыми файлами, API и проверками. Не считать весь backlog
  утверждённым дизайном или разрешением на изменение системных соединений.
- Для изменяемого поведения сначала воспроизвести требование тестом на существующем fake
  или новой узкой fixture: RED → минимальная реализация → GREEN → рефакторинг.
- Проверять пользовательский результат и отказные сценарии, не дублировать реализацию тестами.
- Для каждой новой команды обновить общий реестр, меню и `/help`; для настроек — GUI,
  хранение, валидацию и README. Описать миграцию и ограничения возврата к старой версии.
- VPN, сеть, распознавание и доставка должны иметь fake-реализации для обычного CI;
  реальные VPN не переключаются во время unit-тестов.
- Команды проверок выше — требования к будущей реализации, а не отчёт о выполненных тестах.

Общие проверки из `.github/workflows/ci.yml` для реализованных изменений:

```bash
cargo fmt --all --check
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo test --workspace --locked
```

Ожидаемый результат: PASS на поддержанных платформах; проверка зависимостей cargo-deny
в CI также проходит. Живые/ignored-тесты с агентами запускаются отдельно.
