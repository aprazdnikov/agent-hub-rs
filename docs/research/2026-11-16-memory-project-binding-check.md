## Реализовано

- Явный Move после физического перемещения checkout и Share для выбранного worktree.
  Без подтверждения нет связи; remote, название и файлы репозитория не используются.
- Реестр вне репозитория, стабильный прежний ID, прямые привязки без цепочек.
  Snapshot, история, источники, политика, tombstones и копия v1 остаются на месте.
- Общий resolver для Store/MemoryReader: GUI, Telegram, пять harness и отдельный CLI.
- GUI с preview и подтверждением; CLI `--memory-project move|share` с токеном.
  Привязка проверяется при дальнейшем обращении старых handles текущей версии.
- Занятое назначение отклоняется; устаревший preview не применяется. Блокировки
  реестра/источника/назначения неблокирующие. Повтор не создаёт второго хранилища.
- Состояние показывает связанные каталоги и общую область очистки/удаления.
  Импорт после переноса показывает текущий целевой cwd, не историческую идентичность.

## Итоговое ревью и сбои

Независимый read-only reviewer: gpt-6-astra high. Два Important исправлены:

1. Родитель `.projects` на Unix синхронизируется перед публикацией реестра.
   `parent_sync_publication_failure_keeps_source_binding`: до исправления
   принудительный отказ fsync родителя не мешал ложному успеху; после — отказ
   оставляет исходный проект доступным, назначения ещё нет.
2. При ошибке после rename проверяется опубликованное состояние. Совпадение
   с новым реестром или невозможность проверки даёт отдельную ошибку неопределённой
   публикации с целевым путём. `post_rename_publication_failure_reports_uncertainty_and_destination`:
   до исправления возвращалась обычная I/O-ошибка; после — диагностируемая
   неопределённость, целевая память читается, старый путь отключён.

Оба regression-теста прошли runtime RED → GREEN. Linux-инъекция через тестовую
C-библиотеку LD_PRELOAD действует только в дочернем CLI и временном хранилище.
В production нет тестовых hooks. Это имитация отказа fsync, не физическое отключение
питания. Дополнительно исправлен обнаруженный при проверке интерфейсов старый путь
в preview импорта после Move, отдельный regression runtime RED → GREEN.
Начальные тесты новых API имели RED на отсутствии API при компиляции; полный строгий
runtime RED для всех первоначальных тестов не заявляется.

Minor отложен: обычный GUI-список «Найти / обновить» пока не показывает общую область;
она видна через «Показать состояние и записи». Изменение связано только с отображением.

## Решения и ограничения

- Агент выбрал явный реестр вместо переносимого маркера UUID. Цена: после rename
  требуется один шаг привязки с прежним каноническим путём; автоматического поиска нет.
- Share объединяет всю память и её политику, не отдельные ключи. Цена: изменения
  и удаление видны всем связанным worktree; выборочное копирование — экспорт/импорт.
- Старые бинарники до MEM-04 нужно завершить до привязки. Они не понимают реестр;
  downgrade/одновременное использование старой версии с привязками не поддерживается.
- Нативные Windows/macOS не запускались. Кросс-компиляция не доказывает runtime
  гарантий. Windows наследует переносимый слой: Unix-защита от hardlink/гонок
  подмены и fsync каталогов на него не распространяется. Враждебный процесс того
  же OS-пользователя не изолируется; это прежняя граница персонального хранилища.
- Неизвестный/повреждённый реестр даёт отказ, но удаление реестра вручную не является
  поддерживаемым способом отвязки. Резервная копия должна включать `.projects`.
- Изменения оставлены локально в текущей release-ветке. Commit, push, merge и выпуск
  в этом этапе не выполнялись. Рабочее дерево и ledger сохранены.

## Ручная проверка новой версии

Предыдущие ручные проверки MEM-03 подтверждены пользователем 2026-11-16.
Новые GUI-сценарии MEM-04 пользователем ещё не подтверждены.

1. Завершить старые процессы приложения/MCP и запустить `./target/debug/agent-hub`.
2. Создать запись в отдельном тестовом проекте A. Переименовать A в B.
3. В GUI выбрать B → «Перенос проекта и общая память worktree» → исходный путь A
   → «Перенести привязку» → preview → подтверждение. Прочитать исходную запись в B.
4. Выбрать отдельный пустой тестовый каталог C → источник B → «Подключить общую
   память» → preview → подтверждение. Изменить запись в C; проверить новую ревизию в B.
5. Через «Показать состояние и записи» проверить B/C в списке связанных каталогов.
   Четвёртый несвязанный каталог должен оставаться пустым.
