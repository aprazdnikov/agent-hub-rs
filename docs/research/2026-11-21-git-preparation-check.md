# Проверка подготовки Git — шаг 2.2б

Реализовано локальное явное правило Git для новых задач: выбранные remote/base,
сохранённое намерение подготовки, fetch точной базы, fast-forward локальной базы,
новая рабочая ветка, сохранённый SHA. Подготовка отделена от запуска модели.
Перед запуском асинхронно проверяются ветка и история; перед первым запуском —
также чистота и точный SHA. При продолжении допускаются результаты работы агента.

Состояния и правила сохраняет прежний actor в topics.tasks.json. Рабочий процесс
не пишет файл задач. После перезапуска нет повторов Git и автоматического запуска
модели. При неизвестных/частичных эффектах требуется проверка человеком.

## Автоматические проверки

`cargo test --workspace`: **2033 passed, 15 ignored, 50 наборов**, exit 0.
`cargo fmt --check`, `cargo clippy --workspace --all-targets -- -D warnings`,
`git diff --check`, `cargo build -p hub-app`: успешны. Собран target/debug/agent-hub.

Git-тесты использовали временные локальные bare-репозитории и worktree. Репозиторий
приложения не переключался; commit/push этого проекта не выполнялись. GUI проверен
headless-тестами egui, ручная проверка нового шага пользователем ещё не подтверждена.
Проверки выполнены на Linux; нативный запуск на Windows/macOS этим отчётом не подтверждается.

Проверены обновление базы, точный регистр, грязное дерево, существующая ветка,
локальные коммиты впереди remote, worktree, отмена, ошибка записи намерения,
перезапуск без повтора, отдельный запуск после подготовки, отказ вне текущего
корня проектов, сохранение черновика следующего шага после ошибки проверки.

Независимая проверка выявила шесть проблем; все исправлены с RED→GREEN:

1. Совпадение имени ветки и тега: используются полные refs/heads/...; рабочее
   дерево не отстаёт от сдвинутой базы из-за неоднозначного короткого имени.
2. Detached worktree с rebase: проверяются незавершённые операции во всех
   доступных связанных worktree, даже если поле branch отсутствует.
3. Параллельный handoff/snapshot: общий отказ работает в точках входа и callbacks.
4. Изменённый workspace_root: перед worker проверяется текущая граница проекта;
   изменение настроек во время работы отменяет операцию.
5. Дополнительные remote refmap: fetch использует --refmap= и --no-prune.
6. Повторная подготовка из GUI: до первой попытки можно выбрать новое имя ветки,
   даже если прежняя подготовка была успешной, но ветка впоследствии изменилась.

Дополнительно предотвращена перезапись игнорируемых файлов при merge/switch.
Диагностика неуспешной проверки не удаляет введённый следующий шаг; после успешного
реального запуска прежняя диагностика очищается. Старые полные файлы задач
по-прежнему читаются и восстанавливаются. Незакрытых замечаний этой проверки нет.

## Безопасность и надёжность

Git вызывается аргументами без shell, через существующий runner с управлением
деревом процессов и ограниченным выводом. Парольный ввод отключён, SSH BatchMode;
stderr/remote URL не сохраняются в истории. Локальные hooks и рекурсивное обновление
submodule отключены. Нет reset, stash, rebase, удаления веток или push.

Намерение записывается до worker; неизвестный результат записи блокирует операции.
Завершение связывается с ticket, ревизией задачи, правилами, темой и настройками;
проверка, отменённая или устаревшая до запуска, не запускает модель.

Хаб блокирует собственную конкурирующую работу, но не чужие терминалы и программы.
Между Git-командами нет общей транзакции: при ошибке база или remote-tracking ref
могли обновиться. Проверки повторяются; update-ref использует ожидаемый прежний SHA.
Не изменяйте репозиторий одновременно из другой программы.

## Ручная проверка

1. Полностью завершите старый экземпляр и запустите target/debug/agent-hub.
2. Для безопасной проверки выберите отдельный чистый Git-проект с настроенным
   remote. В «Задачи → Правила проекта» включите требование подготовки Git,
   укажите remote и точное имя существующей базы, сохраните.
3. Создайте новую задачу с поручением «Прочитай README, ничего не меняй».
   Укажите уникальную рабочую ветку, нажмите «Подготовить ветку Git».
4. Дождитесь «Ветка подготовлена», сверьте имя, SHA и текущую ветку в терминале.
   Убедитесь, что модель сама не стартовала. Отдельно нажмите запуск задачи.
5. Для другой новой задачи создайте незакоммиченный файл и повторите подготовку:
   ожидается понятный отказ, файл должен остаться. Затем самостоятельно уберите
   или сохраните этот тестовый файл.
6. Проверьте ошибку существующего имени ветки, отмену и сохранность статуса после
   перезапуска. При частичных эффектах проверьте git status и ветки перед повтором.
