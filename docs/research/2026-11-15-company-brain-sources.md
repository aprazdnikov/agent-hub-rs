# Переносимая память проекта: технические предпосылки

Дата проверки: 2026-11-15. Исследовательская заметка, не утверждённый дизайн. Проверены первичные источники; совместимость конкретных версий клиентов экспериментально не проверялась.

## Agents SDK и harness

- **Подтверждено:** OpenAI Agents SDK — библиотека для создания агентных приложений; доступны Python и TypeScript. Документация описывает agent loop, состояние, orchestration/handoffs и guardrails. [Agents SDK](https://developers.openai.com/api/docs/guides/agents/sdk).
- **Подтверждено для Codex:** OpenAI описывает общий Codex harness и App Server для разных поверхностей Codex. Agents SDK может выступать клиентом Codex через MCP. Для полного интерфейса сессий и обновлений diff OpenAI рекомендует App Server. [Unlocking the Codex harness, 2026-02-04](https://openai.com/index/unlocking-the-codex-harness/). Публичный `codex-core` реализует бизнес-логику Codex на Rust. [Исходный README](https://github.com/openai/codex/blob/main/codex-rs/core/README.md).
- **Вывод:** исполнение агентов можно делегировать готовому harness, сохранив собственный слой данных и интеграций. Архитектура OpenAI Agents API разделяет hosted harness, environment и application server. [Agents API architecture](https://developers.openai.com/api/docs/guides/agents-api/architecture).

## Progressive disclosure и два инструмента

- **Подтверждено:** Anthropic описывает загрузку определений инструментов по необходимости, включая `search_tools` с уровнями детализации. Также можно фильтровать большие результаты в исполняемом коде до передачи модели. Само исполнение кода требует sandbox, лимитов ресурсов и наблюдения. [Code execution with MCP, 2025-11-04](https://www.anthropic.com/research/code-execution-with-mcp).
- **Подтверждено:** нативный Tool Search использует `defer_loading`; после поиска конкретные определения загружаются в контекст. Поиск добавляет отдельный шаг и задержку; выгода зависит от размера каталога и задач. [Advanced tool use, 2025-11-24](https://www.anthropic.com/research/advanced-tool-use).
- **Вывод:** фасад `discover` + `invoke` — допустимый вариант собственного API, но число «два» не является требованием MCP или гарантией качества. Нативный tool search и универсальный dispatcher — разные реализации. MCP описывает инструменты через имена, схемы входа/выхода и метаданные. При сокрытии операций за одним `invoke` проверку схем, права на каждую операцию и журналирование нужно сохранить на сервере; клиент видит менее подробную поверхность. [MCP Tools, версия 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/server/tools).

## Совместимость и выполнение

- **Подтверждено:** MCP определяет `stdio` и Streamable HTTP. В первом случае клиент запускает дочерний процесс; во втором сервер существует самостоятельно и обслуживает подключения. Наличие MCP само по себе не означает доступность одного локального процесса из любого клиента. [MCP Transports, версия 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports).
- **Подтверждено на дату проверки:** актуальные OpenAI docs указывают STDIO и Streamable HTTP для ChatGPT desktop, Codex CLI и IDE extension, включая bearer/OAuth для HTTP. ChatGPT web использует remote MCP через plugins; hosted plugin tools могут иметь другие возможности. Поэтому утверждение «ChatGPT вообще поддерживает только remote» слишком широкое. Документация отдельно предупреждает, что одного remote MCP недостаточно для web-совместимости plugin. [MCP в ChatGPT и Codex](https://learn.chatgpt.com/docs/extend/mcp).
- **Подтверждено:** MCP authorization описывает транспортную авторизацию HTTP на базе OAuth; для STDIO предполагаются credentials из окружения. Сервер обязан проверять предназначение токена; передавать входящий токен без изменений в downstream API запрещено. **Вывод:** корпоративные ACL, доступ к документам и делегирование прав остаются обязанностью Company Brain и интеграций. [MCP Authorization, версия 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization).
- **Подтверждено:** в спецификации 2025-11-25 есть экспериментальные Tasks с долговечным состоянием, polling и отложенным результатом. Они требуют согласования capabilities; нельзя предполагать поддержку каждым клиентом. **Вывод:** для фоновых jobs нужны явно выбранные серверные execution/state и путь получения результата; MCP-фасад этого автоматически не создаёт. [MCP Tasks](https://modelcontextprotocol.io/specification/2025-11-25/basic/utilities/tasks).

## Общий контекст и swarm

**Вывод:** общий доступ к знаниям обеспечивает общие исходные данные, но сам по себе не задаёт распределение работы, владельца результата, обмен результатами и восстановление после сбоев. Первичный пример Anthropic использует lead agent, делегирование и отдельные контексты subagents, а затем синтез результатов. Это пример реализации, не требование единственной архитектуры. [Multi-agent research system, 2025-06-13](https://www.anthropic.com/research/multi-agent-research-system).

## Граница рекомендации

Независимый слой знаний и разрешённых действий с MCP-интерфейсом позволяет использовать готовые клиенты и runtime для исполнения агентов. Совместимость следует проверять для конкретных клиентов: подключение, права, обнаружение инструментов, передача результатов и восстановление долгих операций.

## Применение в agent-hub

Целевой сценарий — собственная работа разработчика, управляющего разработкой с агентами; командное использование возможно позднее.

Для проекта выбрана переносимая память через независимый MCP-сервис. Подключённый агент формулирует записи и сводки; сервис хранит данные, выполняет поиск, проверяет версии и возвращает источники. Поиск по тексту и метаданным не требует отдельных LLM-вызовов. Статус работы и следующий шаг хранятся как записи памяти. agent-hub сохраняет роль запуска CLI и взаимодействия через Telegram.

Приёмочный сценарий: две свежие сессии разных harness используют одну память; второй агент восстанавливает цель, принятые решения и следующий шаг со ссылками на источники. Данные переживают закрытие сессий и перезапуск сервиса.
