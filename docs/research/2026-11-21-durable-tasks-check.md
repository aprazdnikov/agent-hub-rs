# MEM-07 — проверки задач и ручных запусков

Дата: 2026-11-21. Реализация локальна поверх db6799e и незакоммиченного MEM-06.
[Дизайн](../specs/2026-11-21-durable-tasks-design.md) ·
[План](../plans/2026-11-21-durable-tasks.md) · [Руководство](../guide/tasks.md).

## Реализовано

- Отдельная TaskBook v1 и `topics.tasks.json`; ID задачи и номера попыток независимы
  от темы и session ID. Проект/агент назначаются при создании по выбранной теме.
- Сохранение намерения до запуска модели; точная ревизия, один управляемый запуск,
  явный следующий шаг для продолжения. Автоматического повтора после сбоя нет.
- Состояния, итоговый текст или диагностика отсутствия текста; восстановление
  незавершённых попыток в прерванные. Результат запуска не объявляет приёмку человеком.
- GUI «Задачи» и Telegram `/task`; текущие механизмы разрешений/вопросов сохранены.
  Создание и просмотр не запускают модель. Для обоих интерфейсов нужен работающий бот.

## Автоматические проверки

`cargo test --workspace --locked`: **1973 passed, 0 failed, 15 ignored**, 49 suites.
Clippy, `cargo fmt --all -- --check`, debug- и release-сборки прошли.
Полный прогон выполнен после исправлений ревью. Последующие правки двух завершающих
точек с запятой для Clippy не меняют поведение. Проверены:

- pure model: stale revision, параллельный запуск, история, точный номер попытки,
  отказ от устаревшего завершения, лимиты и неизвестный формат;
- файл: sidecar переживает открытие, не создаётся при чтении отсутствующих данных,
  повреждённый файл не заменяется, topics.json не изменяется;
- актор: создание без запуска, сохранение до запуска, replay refusal, перезапуск
  без модели, результат после перезапуска, чужой проект/агент, stale GUI scope,
  отказ записи до запуска, проверка Telegram allowlist;
- GUI: остановленный бот, ответ старого scope, защита от повторного pending-запроса,
  черновик другого проекта и следующий шаг другой ревизии;
- review regressions: многострочный текст, переполнение ответа, полный snapshot,
  отложенный альбом, прекращение выдачи при отзыве доступа.

Начальный RED модели был ошибкой отсутствующего API. Основные интеграционные тесты
добавлялись после реализации; весь этап не заявляется строго test-first.
Все семь исправлений ревью имели наблюдаемый runtime RED → GREEN.
Пользовательские данные, работающий процесс и реальные модельные сессии не менялись.

## Независимое ревью

Read-only ревью gpt-6.2-astra high: без Critical, семь Important исправлены одной
итерацией с регрессионными тестами:

1. Telegram сохраняет переносы и отступы свободного текста.
2. Черновик создания очищается при смене scope и после успешного создания.
3. Черновик следующего шага не переносится на новую ревизию.
4. Ответ больше 64 КиБ сохраняет явную диагностику отсутствия полного результата.
5. Завершению попытки зарезервировано место; валидный полный файл восстанавливается
   через компактную сериализацию и служебный резерв. Отказ по лимиту не блокирует чтение.
6. Вложения/альбомы/голосовые, пришедшие во время управляемой задачи, отклоняются
   до буферизации и не запускают модель после завершения попытки.
7. Перед каждой частью карточки проверяется текущий доступ; выдача отменяется
   при shutdown. Уже отправленная часть не отзывается.

Один Minor отложен: Telegram показывает состояния прошлых попыток, но полный текст
только последней. Шаги и тексты всех попыток доступны в GUI; отдельной команды просмотра
конкретной старой попытки пока нет.

## Принятые границы

- Сеть/команда отложены пользователем; другие независимые writers не поддерживаются.
  Единственный экземпляр приложения и актор обеспечивают последовательность записи.
- Сбой внешнего действия модели нельзя превратить в exactly-once гарантию.
  Прерванная попытка требует проверки эффектов и явного продолжения.
- На Unix публикация дополняется fsync каталога; нативная Windows power-loss проверка
  не выполнялась. Автоматическая атомарная замена не равна такой проверке.
- MEM-06 и подготовленные ранее release-документы сохранены; это ревью их не повторяет.
  Сравнение двух реальных harness, живой Telegram и ручной GUI остаются пользователю.
- Записи задач не входят в MCP-память, экспорт памяти, `/save` или Move/Share.
  Поручения и последние ответы сохраняются без фильтрации секретов; полный диалог не копируется.

## Ручная проверка перед релизом

1. Перезапустить новую сборку, запустить бота. Выбрать отдельную тему Qwen с тестовым
   проектом, содержащим README.md. Открыть «Задачи», выбрать эту тему.
2. Создать «Проверка README» с поручением: «Прочитай README.md, назови первый заголовок.
   Ничего не изменяй». Ожидается новая карточка; модель ещё не запущена.
3. Нажать запуск. Дождаться результата и сверить заголовок. В истории одна завершённая
   попытка. В Telegram `/task` и `/task get ID` показывают ту же задачу и ревизию.
4. Перезапустить приложение/бота: задача и результат сохранились, нового запуска нет.
5. Ввести следующий шаг: «Назови разделы README, ничего не изменяй». Продолжить.
   Ожидается новая попытка; после ответа поле шага пусто. Старый результат виден в GUI.
6. Для отдельной тестовой задачи нажать `/stop` во время выполнения. После завершения
   остановки/перезапуска попытка прервана; автоматической новой попытки нет. Перед
   продолжением явно проверить прежние эффекты и указать новый шаг.
7. Повторить старую `/task run ID РЕВИЗИЯ`: получить отказ, а не ещё один запуск.
   Попытка запуска из темы другого проекта/агента также должна дать отказ.

Ответ пользователя: GUI создание/запуск/история; Telegram просмотр/продолжение;
сохранность после перезапуска; остановка без автоповтора; версия/модель; ошибки/неудобства.
