# Развитие задач после 1.0.0

Статус: решение принято пользователем; этап 1 реализован и автоматически проверен, шаг 2.1 (передача и предпросмотр) реализован; шаг 2.2а (правила проекта) реализован; шаг 2.2б (проверяемая подготовка Git) реализован; шаг 3.1 (локальное управление задачами) реализован; шаг 3.2 (настольный запуск и разрешения) реализован и автоматически проверен; шаг 3.3 (продолжение общей задачи через Telegram) реализован и автоматически проверен; ручная приёмка нового шага ожидается.

Пользователь выбрал выполнение всех направлений поэтапно: управление задачами,
передача другому агенту, затем настольная работа без Telegram. Конкретный пример
повторяемого указания: обновлять базовую ветку перед созданием рабочей ветки.
Это постоянное правило проекта, а не шаблон повторяющейся задачи.

## Этап 1 — управление задачами

Статус задачи отделён от состояния попытки: «Запланирована», «Нужна проверка»,
«Принята», «Отложена». Новая задача запланирована; окончание любой попытки,
включая восстановление после аварии, требует проверки. Приёмку устанавливает
только явное действие человека. Из принятой или отложенной задачи сначала явно
возвращаются к работе. Архив — отдельный признак; история сохраняется.
Архивирование и смена статуса выполняющейся задачи запрещены.

GUI и Telegram позволяют искать по названию и поручению, фильтровать по статусу
и архиву, читать результат конкретной попытки. По умолчанию архив скрыт;
явное чтение по ID доступно. Архив не освобождает существующий лимит 100 задач.
Операции изменения требуют актуальной ревизии и сохраняются до подтверждения.
Старые файлы задач читаются без потери ID, поручений и истории. Старые задачи
без попыток считаются запланированными, с попытками — требующими проверки.

## Этап 2 — правила проекта и передача агенту

Правила принадлежат проекту, имеют редакцию и явно включаются пользователем.
Перед запуском видны поручение, правила и передаваемый контекст. В попытке
сохраняется применённая редакция правил; изменение правила не переписывает историю.
Передача другому агенту сохраняет ID задачи и попытки с указанием исполнителя.
Разрешения предыдущего агента не переносятся. Запуск остаётся ручным.

Первое правило: подготовка Git перед новой задачей разработки.

1. Определить репозиторий, выбранный remote и точное имя базовой ветки.
   `Dev`, `dev`, `master` и `main` не считать взаимозаменяемыми.
2. Проверить незакоммиченные изменения. Не удалять их и не прятать автоматически.
3. Получить обновления remote; при сетевой ошибке не создавать ветку от устаревшей базы.
4. Обновить локальную базовую ветку только fast-forward. При расхождении истории
   остановить подготовку и показать понятную причину; не выполнять reset/rebase.
5. Создать рабочую ветку от обновлённой базы. Показать базовую ветку, SHA и имя
   созданной ветки. При занятости базы другим worktree не переключать её скрытно.

Для этого репозитория локально наблюдается `main` и `origin/HEAD -> origin/main`.
Это наблюдение не назначает `main` базой всех проектов. Настройка базы должна быть
явной; предложенное значение можно получить из remote HEAD.

Существующая процедура MEM-06 `continue-work@1` — копируемая инструкция,
не механизм автоматического исполнения. Передача текста модели не гарантирует
соблюдения Git-правила. Проверяемую подготовку Git следует выполнять отдельным
локальным шагом до запуска агента, с отображением результата. Подробный план
этого этапа составляется после этапа 1 и проверки интерфейса запуска.

## Этап 3 — настольная работа без Telegram

Сначала создание, чтение и управление задачами без запущенного бота; затем запуск,
остановка, вопросы и разрешения в GUI. Владелец хранилища остаётся единственным:
GUI и Telegram используют общий сервис, не два независимых writer.
Перезапуск не повторяет внешние действия автоматически.

Шаг 3.1: режим «Локально», явный выбор каталога и агента, управление задачами,
правилами и историей без токена/темы. GUI и Telegram используют один TaskService.
Настроенный корень проектов соблюдается; ошибка загрузки настроек не снимает
ограничение, а блокирует локальный доступ до исправления/сохранения настроек.
Ошибка хранения блокирует оба клиента до полного перезапуска приложения.
Шаг 3.2 добавляет запуск моделей, подготовку Git, остановку, вопросы и разрешения
без Telegram. Шаг 3.3 объединяет GUI и Telegram одним исполнителем: подключение
бота не прерывает задачу и не повторяет запуск. Каждая попытка начинает свежую CLI-сессию с контекстом задачи. Явное
разрешение связано с уникальным запросом и не переживает отмену/таймаут. Общее
редактирование настроек без реквизитов Telegram и передача файлов в GUI остаются
за границами этого шага; CLI по умолчанию запускается без реквизитов Telegram.

Шаг 3.3: `/task follow ID` подписывает тему того же проекта на текущую задачу.
Ответы на запросы принимает подписавшийся пользователь; GUI использует тот же
одноразовый запрос. `/stop` действует для разрешённого пользователя в рамках
проекта, даже без подписки. Отдельный исполнитель или сетевой сервер не добавляются.
Следующий шаг запускается вручную с текущей ревизией задачи. Остановка бота не
останавливает исполнение; выход приложения останавливает его без автоповтора.

## Общие границы

- Сеть для удалённых клиентов, автоматическая очередь и параллельные управляемые
  запуски остаются вне этих этапов. Git fetch — отдельная операция подготовки.
- Интерфейс и сообщения ошибок на русском, включая выбранные значения списков.
- Секреты и полные диалоги не добавляются в историю автоматически.
- Каждый этап имеет автоматические тесты и отдельную инструкцию ручной проверки.
- Этот документ не подтверждает реализацию или ручную проверку новых возможностей.
