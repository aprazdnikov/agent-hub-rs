# Релизы

[Каталог документов](../README.md) · [Хронология](../history.md) · [Открытые проверки](../roadmap/README.md)

Файлы `v<версия>.md` содержат готовый текст для GitHub Releases. Служебные статусы,
навигация по документации и журнал подготовки находятся здесь и не попадают в описание
релиза. Наличие файла или тега само по себе не подтверждает готовность сборок.

|---|---|---|---|
| v0.8.0 | [Удобнее управлять задачами с телефона](v0.8.0.md) | 2026-11-05: пользователь поручил создать тег с подготовленным текстом; версия workspace обновлена до 0.8.0 | [Страница релиза](https://github.com/aprazdnikov/agent-hub-rs/releases/tag/v0.8.0), [запуски Release](https://github.com/aprazdnikov/agent-hub-rs/actions/workflows/release.yml) |

Пока workflow не завершился успешно и на странице нет файлов, выпуск не считается
завершённым. До первой публикации ссылка на страницу может возвращать 404.

## Порядок выпуска

1. Подготовить текст `docs/releases/v<версия>.md`, обновить версию workspace в
   `Cargo.toml` и записи workspace-пакетов в `Cargo.lock`.
2. Проверить изменения и релизную сборку; убедиться в успешном CI. Результаты ручных
   проверок и их ограничения указывать отдельно.
3. Согласовать сообщение релизного коммита, создать коммит в `main` и отправить его.
4. Создать аннотированный тег `v<версия>` на этом коммите и отправить тег в origin.
5. Дождаться workflow Release: он проверяет совпадение версии с тегом и наличие
   непустого текста, собирает Windows, Linux и две архитектуры macOS, затем публикует
   файлы и описание из Markdown. Автоматическая генерация описания выключена.
6. Проверить целевой коммит тега, текст GitHub Release и список файлов с SHA-256.
   При сбое сборки исправить причину; не перемещать опубликованный тег молча.

## Подготовка v0.8.0

- Версия меняется только у девяти пакетов workspace; сторонние зависимости не обновляются.
- Публикация читает текст из того же тега, из которого собраны файлы. Отдельный checkout
  в job `publish` делает Markdown доступным после загрузки артефактов.
- Подготовленное описание сохранено; убраны только служебные пометки и заменена ссылка
  сравнения на `v0.7.1...v0.8.0`.
- Проверки реального автозапуска, распознавания и передачи задач остаются открытыми
  в [roadmap](../roadmap/README.md).
- Перед тегом CI обнаружил ошибку проверки версии macOS в JXA: нативный тест завершился
  сообщением `Unknown macOS version`. Проверка версии через поля структуры заменена
  на поиск класса `SMAppService` через `NSClassFromString`; отсутствие API даёт прежний
  режим legacy. Сам тест сохранён и должен пройти на macOS перед отправкой тега.

Контракт публикации: [`softprops/action-gh-release@v2`](https://github.com/softprops/action-gh-release/blob/v2/action.yml), параметры `body_path` и `generate_release_notes`; проверен 2026-11-05.

## Локальные проверки подготовки, 2026-11-05

- `cargo build --release --locked -p hub-app` — PASS на Linux.
- `cargo test --workspace --locked` — PASS: 1706 тестов, 13 явно пропущены.
- `cargo clippy --workspace --all-targets --locked -- -D warnings`, форматирование
  и `git diff --check` — PASS.
- Метаданные Cargo и сравнение lockfile подтверждают версию 0.8.0 у девяти пакетов
  workspace без изменения сторонних зависимостей.
- YAML и синтаксис shell-шагов проверены. Шаг перед сборкой принимает v0.8.0,
  отклоняет несовпадающий тег и отсутствие файла описания.
- Ссылки и навигация документации проверены; содержательная часть текста релиза
  совпадает с ранее подготовленной. CI и сборки на GitHub проверяются отдельно.
- Исправленный скрипт проверки разрешений проверен локально на поддельном Objective-C
  мосте: четыре состояния, отсутствие API, неизвестный и неверно типизированный ответ.
  Старый скрипт не проходил пять сценариев, новый проходит все семь. Это не заменяет
  нативный macOS-тест; 21 локальный тест адаптера автозапуска прошёл отдельно.
