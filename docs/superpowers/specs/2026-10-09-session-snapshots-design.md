# Снимки сессий

## Цель

Одной командой сохранить всё о сессии темы — данные хаба и историю самого агента — в каталог снимков, посмотреть список снимков и развернуть снимок в новой теме, продолжив работу. Работает для всех бэкендов: Claude, Codex, Qwen, Hermes. Выходит в релизе 0.5.0.

## Решения

| Вопрос | Решение |
|---|---|
| Что в снимке | Бэкенд, рабочий каталог, id сессии, название темы, дата, версия агента и копия файлов истории агента. Файлы проекта не сохраняются |
| Семантика восстановления | Перенос: одна сессия — одна тема. Если другая тема ещё привязана к этой сессии, она сбрасывается (как `/reset`) и получает уведомление |
| Как восстанавливать | Пользователь сам создаёт тему и пишет в ней `/restore <имя>`; бот темы не создаёт |
| Формат | Каталог на снимок: `manifest.json` + `agent/`; без архивов и отправки в Telegram |
| Где хранить | `[snapshots] dir` в настройках, по умолчанию `~/.agent-hub`; снимки — в `<dir>/snapshots/<имя>/` |
| Данные агента при восстановлении | Не перезаписываются: если сессия у агента есть — только перепривязка; файлы из снимка возвращаются, только если сессии у агента нет |
| Hermes | Полный перенос строк `state.db` через Python-API самого Hermes |
| Во время хода | `/save` и `/restore` отказывают; пока снимок пишется или возвращается, в теме не стартует ход и отказывают `/new`, `/cwd`, `/reset`, `/backend` |
| Конкуренция за сессию | На время `/save` и `/restore` сессия **резервируется** в `Hub` (не только тема): второй `/save`/`/restore` той же сессии и ходы в любой теме, привязанной к ней, отказывают до снятия резерва |
| Сохранение привязок | Перепривязка при `/restore` транзакционна: новое состояние тем сначала записывается в `topics.json` с проверкой результата, и только потом меняется память и уходят сообщения; ошибка записи — привязки прежние, пользователю сообщение об ошибке |

## Команды

| Команда | Поведение |
|---|---|
| `/save [имя]` | Снимок сессии темы. Имя по умолчанию — `<название темы>-ГГГГММДД-ЧЧММ` (местное время), транслитерированное и приведённое к `[a-z0-9._-]`, не длиннее 64 символов; название темы хаб знает только из `forum_topic_created` текущего запуска — без него вместо названия имя бэкенда (`claude-20261009-1530`). Занятое имя — отказ. Нет сессии — «Нечего сохранять: в теме ещё нет сессии». Успех — «💾 Сохранено: <имя> · <бэкенд> · <каталог>» |
| `/saves` | Не больше 30 снимков, новые сверху: имя, бэкенд, каталог, дата, исходное название темы. Пусто — «Снимков пока нет» |
| `/restore <имя> [каталог]` | Привязывает тему к сессии из снимка. Каталог — из снимка или указанный (разрешается как у `/new`, должен существовать и быть внутри `workspace_root`). Старой теме — «Сессия перенесена в другую тему». Успех — «♻️ Восстановлено: <имя> · <бэкенд> · <каталог>» |

Все три — только внутри темы. Во время хода — «Дождитесь конца хода или /stop». Если к концу `/restore` тема-владелец сессии выполняет ход, привязки не меняются (сессия занята в другой теме); уже возвращённые агенту файлы остаются, повтор `/restore` только перепривяжет. Команды попадают в `/help` и меню бота через `Command::ALL`.

## Снимок на диске

```
<dir>/snapshots/<имя>/
  manifest.json
  agent/…
```

`manifest.json`:

```json
{
  "version": 1,
  "name": "fix-tests-20261009-1530",
  "created_at": "2026-10-09T15:30:12Z",
  "title": "Починить тесты",          // null, если название неизвестно
  "backend": "claude",
  "cwd": "/home/me/Projects/shop",
  "session_id": "…",
  "agent_version": "2.1.292",
  "backend_data": {"kind": "claude", "project": "-home-me-Projects-shop"},
  "files": ["projects/-home-me-Projects-shop/<id>.jsonl", "…"]
}
```

- `backend_data` — по варианту на бэкенд: Claude `{project}`, Codex `{}`, Qwen `{}`, Hermes `{profile: Option<String>}` (информационно: возврат идёт в текущий профиль из настроек). `backend` выводится из `backend_data.kind`, несовпадение — ошибка разбора.
- `created_at` — UTC; `files` — не больше 10 000; `manifest.json` — не больше 1 МиБ. Оба лимита проверяются и при записи, до публикации снимка, и при чтении.
- `files` — относительные пути внутри `agent/`, без `..` и абсолютных путей.
- Запись атомарна: `snapshots/.tmp-<uuid>/` → `rename` в `snapshots/<имя>/`. Ошибка — временный каталог удаляется.
- Права (Unix): `snapshots/` и каталоги снимков `0700`, файлы `0600`.

## Бэкенды

Корень хранилища агента вычисляет отдельная функция (окружение ∨ значение по умолчанию) и передаёт в `SessionArchive` явно. Копируется только перечисленное (белый список), символьные ссылки пропускаются.

| Бэкенд | Выгрузка в `agent/` | `present` | Возврат |
|---|---|---|---|
| Claude (`$CLAUDE_CONFIG_DIR` ∨ `~/.claude`; относительное значение — отказ) | `projects/<P>/<id>.jsonl` и `projects/<P>/<id>/` (субагенты, tool-results). `<P>` — поиском `projects/*/<id>.jsonl` (кодирование длинных путей включает хэш, хаб его не вычисляет); записывается в манифест. `file-history/` не берётся | ровно один `projects/*/<id>.jsonl` | В `projects/<P из манифеста>/`. Claude ≥ 2.1.223 ищет id по всем проектам, поэтому новый `cwd` не мешает. Больше одной копии — отказ |
| Codex (`$CODEX_HOME` ∨ `~/.codex`; относительное значение — отказ) | все `sessions/**/rollout-*-<id>*.jsonl[.zst]`; базы SQLite не трогаются; rollout вне `sessions/ГГГГ/ММ/ДД/` с датой из имени — отказ `/save` (его нельзя вернуть) | файл в `sessions/`; только в `archived_sessions/` — ошибка «Сессия в архиве Codex: выполните `codex unarchive <id>`» | В `sessions/ГГГГ/ММ/ДД/` по дате из имени файла, имя прежнее. Codex находит файл по id и сам создаёт запись в базе |
| Qwen (`$QWEN_RUNTIME_DIR` ∨ `$QWEN_HOME` ∨ `~/.qwen`; относительные значения — отказ) | `projects/<san(cwd)>/chats/<id>.jsonl` и спутники `<id>.*`, кроме `.runtime.json` и `.worktree.json`; `projects/<san(cwd)>/subagents/<id>/`; `todos/<id>.json` | файл в `projects/<san(cwd назначения)>/chats/` **и** его первая запись содержит этот `sessionId` и `cwd`, равный каталогу назначения; файл с этим id, но другим `cwd` (совпадение `san` для разных путей, например `/work/a-b` и `/work/a_b`) — явный отказ | Решение «переписывать или нет» — по `cwd` из истории, а не по имени каталога проекта. Тот же `cwd` — как есть. Другой — поле `cwd` верхнего уровня переписывается во всех записях JSONL чата и субагентов, файлы кладутся под `san(новый cwd)`. `san`: каждая кодовая единица UTF-16 вне `[A-Za-z0-9]` → `-`; на Windows сначала нижний регистр. Существующий `todos/<id>.json` (он не зависит от каталога проекта) не перезаписывается. Настройка Qwen `advanced.runtimeOutputDir` не поддерживается |
| Hermes (каталог выбирает сам Hermes: `HERMES_HOME`, `--profile`, «липкий» `active_profile`) | `hermes-session.json` — `SessionDB.export_session_lineage(id, include_inactive=True)`: словарь со списком `segments` (линия сжатия) | `get_session(id)` в `state.db` профиля | `SessionDB.import_sessions([сегменты])`, в каждом сегменте подставлены `cwd` и `model_config.cwd`. Лимиты Hermes: ≤ 10 000 сообщений и ≤ 5 МиБ на сессию, ≤ 25 МиБ всего |

### Hermes

- Встроенный в хаб Python-скрипт с подкомандами `present`, `export`, `import`; аргументы — списком, без оболочки; данные — через файлы.
- Запускается окружением самого Hermes (голый интерпретатор не видит его зависимостей):
  - текущие установщики (POSIX-обёртка `hermes`, `hermes.exe`/`hermes.cmd`) — `hermes --run-module cProfile -o <tmp>/profile.out <скрипт> <op> …`; `cProfile` проглатывает код выхода, поэтому результат возвращается только файлом `--result`;
  - классический консольный скрипт pip/uv (shebang с абсолютным путём к `python*`) или `python.exe` рядом с `hermes.exe` — `<python> -I <скрипт> <op> …`.
- Каталог данных скрипт выбирает функциями самого Hermes (как `hermes [--profile P] acp`); хаб передаёт только `--profile` из настроек.
- Скрипт сверяет версию схемы — константу кода и `schema_version` в `state.db` — с проверенной (31); иначе — «Hermes <версия> не поддерживается для переноса».
- Это внутренний API Hermes: поддерживаемые версии ограничены проверенной, есть живой тест.

## Архитектура

### `hub-core`

- `SnapshotName` — newtype, `parse` проверяет `[a-z0-9._-]{1,64}`, не начинается и не заканчивается точкой, основа до первой точки — не имя устройства Windows (`con`, `prn`, `aux`, `nul`, `com1`…`com9`, `lpt1`…`lpt9`).
- `default_name(title, now) -> SnapshotName` — транслитерация кириллицы, обрезка, суффикс времени.
- `Manifest { name, created_at: String (UTC), title: Option<String>, cwd: AbsolutePath, session: SessionId, agent_version, data: BackendData, files: Vec<RelPath> }`; версия (`MANIFEST_VERSION = 1`) и `backend` живут только в JSON: `backend` выводится из `data.backend()`. `Manifest::parse`/`dump` проверяют лимиты, `ManifestError`. `RelPath` — newtype без `..` и абсолютных путей; `BackendData` — enum `Claude { project }`, `Codex`, `Qwen`, `Hermes { profile }`.
- `Command::{Save, Saves, Restore}`, разбор аргументов, тексты.

### `hub-agent`

- Трейт `SessionArchive`:
  - `export(&self, session: &SessionId, cwd: &AbsolutePath, dest: &Path) -> Result<Exported, ArchiveError>` — `Exported { files: Vec<RelPath>, data: BackendData, agent_version: String }`;
  - `present(&self, session, cwd, data: &BackendData) -> Result<bool, ArchiveError>`;
  - `import(&self, session, data, files, src: &Path, cwd) -> Result<(), ArchiveError>` — всё или ничего, откат при сбое.
  - Трейт блокирующий (`Send + Sync`), вызывается из `spawn_blocking`; `Agents::archive(backend, home)` отдаёт `Arc<dyn SessionArchive>` после проверки CLI.
- `ArchiveError` (`thiserror`): `NotFound`, `Ambiguous`, `Archived(String)`, `Occupied { id, cwd }` (у Qwen уже есть другая сессия для этого каталога), `Link(String)` (путь идёт через символьную ссылку), `Unsupported(String)`, `Io(io::Error)`, `Malformed(String)`; `PathError` превращается в `Malformed`.
- Помощники копирования по белому списку (`entry_under`, `open_under`, `create_under`, `collect_tree`, `export_files`, `place_all`): каждая часть пути от доверенного корня проверяется `symlink_metadata`, ссылка — `Link`; каталоги создаются по одной части, файлы — `create_new` с правами `0600` (каталоги `0700`); при сбое созданное удаляется. `export_files` отказывает, если файлов больше `FILES_LIMIT` (столько принимает манифест), до копирования. `place_all` пишет каждый файл под временным именем `.agent-hub-<uuid>.tmp` в его каталоге назначения (`create_new`, `0600`, `sync_all`), затем `hard_link` на окончательное имя (существующее имя — отказ, ничего не перезаписывается) и удаляет временное; файл, по которому агент находит сессию (`present`), кладётся последним.

### `hub-claude`, `hub-codex`, `hub-qwen`, `hub-hermes`

По реализации `SessionArchive` по таблице выше; функция корня хранилища — отдельно.

### `hub-app`

- Настройка `[snapshots] dir` (необязательная, `~` разрешена); `Settings.snapshots_dir: PathBuf` с умолчанием `~/.agent-hub`; поле «Каталог снимков» с выбором папки в GUI.

### `hub-telegram`

- Модуль `snapshots`: `SnapshotStore { root }` (`new(dir)` — корень `<dir>/snapshots`) — `save(name, fill) -> Manifest` (создаёт приватный staging-каталог `.tmp-<uuid>`, отдаёт `agent/` замыканию, проверяет, что манифест читается обратно, пишет `manifest.json`, одно `rename`; staging удаляется при любой ошибке и при `Drop`), `list() -> Vec<Manifest>` (повреждённые пропускаются с `warn`), `load(name) -> Loaded { manifest, agent }`. `SnapshotError`: `Exists`, `Missing`, `Corrupt`, `Manifest`, `Io`, `Archive`. Живёт здесь, а не в `hub-app`: его вызывает `Hub`, а `hub-app` зависит от `hub-telegram`; корень читается из `Settings` на каждую операцию.
- Модуль `transfer`: `SaveJob` и `RestoreJob` выполняют файловую работу в своей задаче под `supervise` (паника задачи всё равно возвращает хабу `crashed`) и отчитываются сообщением `HubMessage::Snapshot(SnapshotDone(Done::…))`: `Saved`, `Loaded`, `Restored`.
- `Hub` обрабатывает три команды и резервирует сессию агента (`Reservation = (бэкенд, id)`) на время файловой работы: второй `/save`/`/restore` той же сессии и ходы тем, привязанных к ней, отказывают или ждут.
- `/save`: отказ во время хода → резерв сессии → `SessionArchive::export` в `agent/` staging-каталога → манифест → атомарное переименование → «💾 Сохранено».
- `/restore`, фаза 1 (`load`): чтение и проверка манифеста, разрешение каталога внутри корня; файлы агента не тронуты. Задача сообщает `Done::Loaded`, хаб выдаёт сессию (`true`) или отказывает (`false`).
- `/restore`, фаза 2 (`apply`, сессия зарезервирована): `present` → `import`, если сессии у агента нет. Результат — `Restoration { name, session, imported }`.
- Перепривязка (`Hub::rebind`) транзакционна и заменяет прежний `put()`: пересчитываются `holders` — другие темы с той же сессией; если эта или любая из них занята ходом или файловой работой, привязки не меняются («сессия занята в другой теме»); иначе строится копия `Topics`, у прежних владельцев сессия сбрасывается, текущая тема привязывается, копия записывается `TopicStore::save`. Только после успеха копия заменяет `self.topics` и уходят сообщения (текущей теме — «♻️ Восстановлено», прежним — «Сессия перенесена в другую тему», без гарантии доставки). Ошибка записи — привязки прежние, пользователю «не сохранены привязки».
- Ошибка импорта или загрузки — темы не меняются. После `Shutdown` хаб не выдаёт сессию новой фазе 2 (файлы агента не трогаются); результат задачи, которая уже получила сессию и отчиталась, пока хаб ждёт конца ходов, применяется как обычно (перепривязка). Результат, пришедший после остановки задачи хаба, теряется: файлы могут быть уже импортированы, привязки — нет; повторный `/restore` идемпотентен (`present` — только перепривязка).
- Отказ перепривязки: тема или прежний владелец выполняет ход — «сессия выполняет ход в другой теме»; занята файловой работой снимка — «с этой сессией работает /save или /restore». Если файлы уже импортированы, к отказу добавляется, что повторный `/restore` только привяжет сессию к теме.

## Безопасность

- В снимок не попадают файлы авторизации (`.credentials.json`, `~/.claude.json`, `auth.json`, `oauth_creds.json`, `mcp-oauth-tokens.json`, `.env`, `settings.json`) и базы целиком — по белому списку.
- Истории — открытый текст (вывод команд, содержимое файлов): права `0700`/`0600`, в логи только имена и размеры.
- Имя снимка и пути в манифесте проверяются: выхода за пределы каталога нет.
- Символьные ссылки проверяются **в каждом компоненте пути** от доверенного корня (каталог снимка, включая `agent/`, и корень хранилища агента), а не только в последнем; любая ссылка — отказ. Каталоги назначения создаются по одному компоненту с той же проверкой, файлы — `create_new`. Гонка с подменой компонента во время копирования не закрывается: для неё нужен процесс того же пользователя, пишущий в каталоги `0700`, — принятый риск.
- Каталог восстановления — внутри `workspace_root`.
- Корни хранилищ из окружения (`CLAUDE_CONFIG_DIR`, `CODEX_HOME`, `QWEN_RUNTIME_DIR`, `QWEN_HOME`) — только абсолютные: относительный путь агент разрешил бы от своего `cwd`, а хаб — от своего.

## Надёжность

- Импорт атомарен по файлу: окончательное имя появляется только у полностью записанного и синхронизированного файла (`hard_link` временного). Падение процесса посреди импорта оставляет не больше временных файлов `.agent-hub-<uuid>.tmp`: агенты их не читают, `present` их не видит, повторный импорт им не мешает (имена уникальны); удаляет их откат только своего запуска, оставшиеся после падения не удаляются.
- Файл присутствия кладётся последним: Claude — `projects/<P>/<id>.jsonl`, Qwen — `projects/<san>/chats/<id>.jsonl`. Прерванный импорт этих бэкендов не выглядит восстановленной сессией, и повторный `/restore` импортирует её заново: уже положенный файл с теми же байтами остаётся как есть (откат его не удаляет — создан не этим запуском), другие байты, ссылка или уже существующий файл присутствия — отказ.
- Остаточный риск Codex: у сессии может быть несколько rollout-файлов, и каждый делает её «присутствующей». Последним кладётся последний по имени (самый поздний), но если процесс упал после первого, `present` уже истинно, и повторный `/restore` только перепривяжет тему к неполной истории. Принято: несколько rollout у одной сессии — редкость (`_<n>`-продолжения), падение посреди импорта — тоже; лечится удалением rollout-файлов сессии и повторным `/restore`.
- Файловые системы без жёстких ссылок (`hard_link` → `Unsupported`) получают прежний путь: окончательный файл пишется копией временного через `create_new`, частичная копия удаляется при ошибке, но падение процесса посреди записи оставит частичный файл. NTFS, ext4, APFS жёсткие ссылки поддерживают; иная ошибка жёсткой ссылки (например, `EPERM` у vfat в Linux) завершает импорт ошибкой с откатом.
- Резервы сессий живут в памяти хаба: перезапуск бота (кнопка «Перезапустить», переподключение после смены настроек) во время `/save`/`/restore` их теряет, а задача снимка доделывает файловую работу без хаба. Принято и вне объёма: `/save` пишет в staging и не портит готовые снимки, импорт не перезаписывает файлы, повторный `/restore` идемпотентен.

## Тесты

- `hub-core`: имя по умолчанию и транслитерация, таблица проверки имени, `RelPath`, манифест туда-обратно и неизвестная версия, разбор команд.
- Бэкенды — на временных «домашних» каталогах: экспорт, `present`, возврат; Qwen — переписывание `cwd`; Claude — две копии → `Ambiguous`; Codex — архивная сессия; Hermes — поддельный интерпретатор и живой тест.
- `SnapshotStore` (`hub-telegram`): атомарная запись и отсутствие мусора при сбое, права, сортировка, повреждённый манифест пропускается.
- `hub-app`: настройка `[snapshots] dir`, старый `settings.toml` без неё читается.
- `hub-telegram`: `/save` → `/restore` в `Hub`, перенос из прежней темы, отказ во время хода, каталог вне `root`, неизвестное имя; резервирование сессии (приостановленный импорт в A и восстановление того же снимка в B; приостановленный экспорт в A, восстановление и ход в B); падающий `TopicStore` — привязки прежние.
- Файловый слой: ссылки в родительских каталогах источника и назначения — отказ, вне корня ничего не создано.
- Qwen: перенос в другой каталог без удаления исходной сессии (`todos` не трогаются); коллизия `san` для `/work/a-b` и `/work/a_b`.
- Манифест: граничные тесты полного цикла записи и чтения по числу файлов и размеру.
- Живые тесты на каждый бэкенд (`#[ignore]`): сохранить → удалить сессию у агента → восстановить → ход видит прежнюю историю.
