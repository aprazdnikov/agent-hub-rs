# Бэкенд OpenCode

## Цель и границы

OpenCode — пятый агент, выбираемый на уровне темы Telegram. Интеграция использует существующий транспорт agent-hub и общие контракты разговора; отдельный сервер OpenCode не запускается. Claude, Codex, Qwen и Hermes сохраняют прежнее поведение.

План реализации: [2026-10-31-opencode-backend.md](../plans/2026-10-31-opencode-backend.md). Эта спецификация описывает реализованный контракт и отдельно отмечает ограничения, а не обещает полную совместимость всех возможностей OpenCode.

## Архитектура

```text
hub-app: настройки, проверка CLI, статус
    └── hub-telegram: HubAgents → OpencodeBackend
            └── hub-opencode: процесс и ACP-адаптер
                    ├── hub-core: доменные типы и настройки
                    └── hub-agent: RPC, Conversation, UserChannel, MCP
```

`hub-opencode` зависит от `hub-core` и `hub-agent`, но не от других бэкендов. Общий ACP-слой `hub-agent` переиспользуется без переноса Hermes-специфичных расширений.

| Модуль `hub-opencode` | Ответственность |
|---|---|
| `backend` | `OpencodeBackend::new(cli, settings)`; `run(session, prompt, inbox, conversation) -> inbox`; запуск процесса, открытие сессии, последовательные ходы, отмена и остановка |
| `protocol` | Параметры ACP, возможности агента, перевод уведомлений в `AgentEvent`, разбор результата prompt |
| `requests` | Привязанный к сессии `Gate`, проверка и обработка разрешений через `UserChannel` |
| `version` | Поиск CLI, разбор версии, ограниченная по времени проверка `opencode acp --version` |

## Процесс и готовность

- Запуск без shell: `opencode acp`; рабочая директория процесса — каталог темы. stdin/stdout/stderr через pipes; включён `kill_on_drop`.
- Протокол — JSON-RPC 2.0, JSON построчно по stdio, общий `hub_agent::rpc::RpcClient`.
- Управляющие запросы имеют тайм-аут 60 с; открытие ограничивается также `Conversation.limits.initialize`. Сам prompt выполняется без RPC-тайм-аута.
- При остановке закрывается RPC, выход процесса ожидается до 2 с, затем процесс завершается принудительно. Уведомление отмены также ограничено 2 с.
- stderr не публикуется произвольным текстом: журнал фиксирует факт и размер строки.
- CLI выбирается из настроек либо `PATH`. Минимальная версия — `1.19.5`; контракт сверялся с установленной сборкой `1.19.5` (живые пробы `initialize`, `session/new`, `session/load`, `session/set_model`, `session/prompt`, `usage`).
- `opencode acp --version` проверяется один раз, не дольше 10 с, и не вызывает модель.

Авторизация, провайдеры и политика разрешений инструментов управляются самим OpenCode (`opencode auth login`, конфигурация). Хаб не устанавливает OpenCode, не изменяет его ключи или конфигурацию.

## ACP-сессия

1. Поднять защищённый MCP-сервер хаба с вопросами и запустить ACP-процесс.
2. Выполнить `initialize`: требуется `protocolVersion: 1` и объект `agentCapabilities`. Поддержка восстановления и изображений определяется по `loadSession` и `promptCapabilities.image`. Клиент не рекламирует файловые и терминальные ACP-возможности.
3. Для новой темы вызвать `session/new {cwd, mcpServers}` и получить непустой `sessionId`. Для сохранённой — `session/load {sessionId, cwd, mcpServers}` при поддержке восстановления.
4. Ошибка загрузки не создаёт новую сессию молча. `session/resume` не используется (он молча создаёт отсутствующую сессию); при отсутствии поддержки восстановления предлагается `/reset`.
5. Если модель задана в хабе, применить `session/set_model` с `modelId` в формате OpenCode (`провайдер/модель`).
6. Режим (агент OpenCode: `build`, `plan`, пользовательские) не переключается хабом: `session/set_mode` не вызывается, выбор остаётся за агентом и его конфигурацией.
7. Отбросить уведомления повторной истории (OpenCode шлёт replay до ответа `session/load`), привязать разрешения к открытой сессии и отправить `SessionStarted`.
8. Выполнить `session/prompt`; изображения передаются как base64 content blocks только при объявленной поддержке. Перед пользовательским содержимым передаётся инструкция пользоваться MCP-инструментами хаба для вопросов и файлов.
9. На локальную отмену отправить уведомление `session/cancel`, закончить разговор и вернуть непрочитанный inbox.

Новые сообщения во время хода остаются в inbox. После `end_turn` адаптер берёт следующий доступный prompt и выполняет его последовательно; пустая очередь завершает разговор. Ошибка, отмена или иной stop reason не запускает следующий ход. Live-steering не поддерживается.

## События и рендер

| ACP | Общий контракт хаба |
|---|---|
| Успешное открытие/загрузка | `SessionStarted(SessionId)` |
| `agent_message_chunk` с текстом текущей сессии | Накопление, затем `AssistantText` перед инструментом и в конце хода |
| `tool_call` | `ToolCall { tool: kind или "tool", summary: title или "OpenCode tool" }`; строки ограничены |
| `end_turn` | `Finished { session, usage: Usage::Opencode { tokens }, background: 0 }` |
| `cancelled` | Без `Finished`; локальная отмена отображается существующим механизмом `/stop` |
| Иной stop reason / ошибка | `Failed` с ограниченным текстом причины |
| `agent_thought_chunk`, `tool_call_update`, `available_commands_update`, `config_option_update`, `usage_update`, чужая сессия | Не публикуются как текст ответа |

Накопленный текст ограничен 8 МиБ. Токены берутся только из `usage.totalTokens` результата prompt; отсутствие значения сохраняется как `None`. Оценочная заполненность контекста из `usage_update` не подменяет это значение. Ошибка провайдера без входа приходит как JSON-RPC `authRequired` (-32000) и отображается подсказкой `opencode auth login`.

Рендер Telegram общий: `Sender::markdown`, `format_finished`, Markdown → Telegram HTML конвейер; отдельного OpenCode-рендера нет.

## Разрешения, вопросы и файлы

- `session/request_permission` принимается только для открытой сессии. Требуются `toolCallId` и уникальные непустые option IDs с предложенными `allow_once` и `reject_once` (проверенный набор OpenCode: `once`/`always`/`reject`).
- `UserChannel::request` возвращает выбор только из предложенных разовых вариантов; «разрешить всегда» не выбирается; неверные формы отклоняются.
- Ожидание пользователя ограничено 5 минутами на уровне адаптера; тайм-аут выбирает разовый отказ. Отмена имеет приоритет над готовым разрешением, закрытый gate не одобряет поздние запросы.
- `McpHttpServer::start_with_questions` включает `send_file` и `ask_user`; OpenCode регистрирует HTTP MCP-сервер хаба через `mcpServers` сессии (`mcpCapabilities.http: true`).
- Сервер слушает только loopback, использует отдельный bearer token на сессию и сохраняет проверки `Host`/`Origin`.

## Доменные и пользовательские контракты

- `BackendKind::Opencode`, каноническое имя `opencode`, включён в `ALL`.
- `Usage::Opencode { tokens: Option<u64> }`.
- `OpencodeSettings { cli: Option<PathBuf>, model: Option<String> }`; поля формы — строки, ошибки — `Field::Opencode(OpencodeField::{Cli, Model})`.
- `[opencode]` в `settings.toml` содержит только `cli`, `model`. Старые настройки без секции читаются с defaults; новые поля для секретов не вводятся.
- Состояние темы сохраняет `backend: opencode` в существующем формате версии 1.
- `/new opencode <путь>`, `/backend opencode` и OpenCode как агент по умолчанию используют существующую маршрутизацию.
- GUI показывает CLI, модель и статус «собственная настройка OpenCode (вход не проверен)». Отсутствие необязательного OpenCode не блокирует запуск другого агента; недоступность выбранного по умолчанию блокирует запуск бота.
- Квоты подписки OpenCode не сообщает: `/limits` показывает «квоты подписки агент не сообщает».

## Ограничения первой версии

- Снимки и перенос сессий (`/save`, `/restore`, `/transfer`) для OpenCode не реализованы: сессии живут в SQLite-базе OpenCode, и их экспорт/импорт — отдельная задача. Команды сообщают «Снимки и перенос сессий OpenCode не поддерживаются».
- Режим/агент OpenCode не выбирается из хаба; `variant` (reasoning effort) не настраивается.
- Фоновые задачи и live-steering не поддерживаются (их нет в ACP OpenCode).

## Проверка и критерии приёмки

Детерминированные тесты покрывают новые и восстановленные сессии, подавление replay, порядок текста/инструментов, игнорирование `available_commands_update`/`config_option_update`/`usage_update`, usage, последовательную очередь, сохранение inbox, EOF, отмену во время открытия и хода, разрешения, MCP-вопросы/файлы и ограниченные CLI-проверки. Core/app/Telegram тесты покрывают команды, совместимость настроек/тем, GUI и обязательность выбранного агента.

Интеграционные gates: `cargo fmt --all --check`, `cargo test --workspace --locked`, `cargo clippy --workspace --all-targets --locked -- -D warnings`, `cargo build -p hub-app --locked`, `git diff --check`.

Живой end-to-end прогон (`AGENT_HUB_LIVE_OPENCODE=1`) выполняется пользователем; успешный результат на Windows/macOS этой спецификацией не заявляется. Контракт ACP сверялся с `opencode 1.19.5` на Linux живыми пробами и разбором встроенного кода `@agentclientprotocol/sdk`.

Вне объёма: общий ACP framework, перенос контекста между агентами, снимки сессий OpenCode, управление входом/ключами/установкой OpenCode из хаба и автоматическое подтверждение опасных действий.
