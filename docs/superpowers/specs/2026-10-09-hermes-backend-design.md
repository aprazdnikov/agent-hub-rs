# Бэкенд Hermes

## Цель и границы

Hermes — четвёртый агент, выбираемый на уровне темы Telegram. Интеграция использует существующий транспорт agent-hub и общие контракты разговора; отдельный Hermes gateway не запускается. Claude, Codex и Qwen сохраняют прежнее поведение.

План реализации: [2026-10-09-hermes-backend.md](../plans/2026-10-09-hermes-backend.md). Эта спецификация описывает реализованный контракт и отдельно отмечает ограничения, а не обещает полную совместимость всех возможностей Hermes.

## Архитектура

```text
hub-app: настройки, проверка CLI, статус
    └── hub-telegram: HubAgents → HermesBackend
            └── hub-hermes: процесс и ACP-адаптер
                    ├── hub-core: доменные типы и настройки
                    └── hub-agent: RPC, Conversation, UserChannel, MCP
```

`hub-hermes` зависит от `hub-core` и `hub-agent`, но не от других бэкендов. Общий слой, выделенный при интеграции Qwen, переиспользуется без переноса Qwen-специфичных расширений.

| Модуль `hub-hermes` | Ответственность |
|---|---|
| `backend` | `HermesBackend::new(cli, settings)`; `run(session, prompt, inbox, conversation) -> inbox`; запуск процесса, открытие сессии, последовательные ходы, отмена и остановка |
| `protocol` | Параметры ACP, возможности агента, перевод уведомлений в `AgentEvent`, разбор результата prompt |
| `requests` | Привязанный к сессии `Gate`, проверка и обработка разрешений через `UserChannel` |
| `version` | Поиск CLI, разбор версии, ограниченные по времени проверки ACP |

## Процесс и готовность

- Запуск без shell: `hermes [--profile NAME] acp`; `--profile` — глобальный аргумент перед `acp`.
- Рабочий каталог процесса и `TERMINAL_CWD` соответствуют каталогу темы. stdin/stdout/stderr передаются через pipes; включён `kill_on_drop`.
- Протокол — JSON-RPC 2.0, JSON построчно по stdio, общий `hub_agent::rpc::RpcClient`.
- Управляющие запросы имеют тайм-аут 60 с; открытие ограничивается также `Conversation.limits.initialize`. Сам prompt выполняется без RPC-тайм-аута.
- При остановке закрывается RPC, выход процесса ожидается до 2 с, затем процесс завершается принудительно. Уведомление отмены также ограничено 2 с.
- stderr не публикуется произвольным текстом: журнал фиксирует факт и размер строки, чтобы не копировать потенциальные секреты.
- CLI выбирается из настроек либо `PATH`. Минимальная версия — `0.21.5`; контракт сверялся с установленной сборкой `0.21.5+9108.g61b7f95`.
- `hermes acp --version` и `hermes acp --check` проверяются отдельно, каждый не дольше 10 с. Они не вызывают модель и не доказывают авторизацию провайдера.

Авторизация, провайдер, память, скиллы и собственные MCP-серверы управляются самим Hermes. Хаб не устанавливает Hermes, не изменяет его sticky-профиль, ключи или конфигурацию и не включает YOLO.

## ACP-сессия

1. Поднять защищённый MCP-сервер хаба с вопросами и запустить ACP-процесс.
2. Выполнить `initialize`: требуется `protocolVersion: 1` и объект `agentCapabilities`. Поддержка восстановления и изображений определяется по `loadSession` и `promptCapabilities.image`. Клиент не рекламирует файловые и терминальные ACP-возможности.
3. Для новой темы вызвать `session/new {cwd, mcpServers}` и получить непустой `sessionId`. Для сохранённой — `session/load {sessionId, cwd, mcpServers}` при поддержке восстановления.
4. Ошибка загрузки не создаёт новую сессию молча. `session/resume` не используется; при отсутствии поддержки восстановления предлагается `/reset`.
5. Если модель задана в хабе, применить `session/set_model`. Затем всегда выполнить `session/set_mode` с `modeId: default`, чтобы восстановленная сессия не сохранила режим обхода подтверждений.
6. Отбросить уведомления повторной истории, привязать разрешения к открытой сессии и отправить `SessionStarted`.
7. Выполнить `session/prompt`; изображения передаются как base64 content blocks только при объявленной поддержке. Перед пользовательским содержимым передаётся инструкция пользоваться MCP-инструментами хаба для вопросов и файлов.
8. На локальную отмену отправить уведомление `session/cancel`, закончить разговор и вернуть непрочитанный inbox.

Новые сообщения во время хода остаются в inbox. После `end_turn` адаптер берёт следующий доступный prompt и выполняет его последовательно; пустая очередь завершает разговор. Сообщение, пришедшее после проверки очереди, остаётся в возвращённом receiver для хаба. Ошибка, отмена или иной stop reason не запускают следующий ход. `craft/drainMidTurnQueue` и live-steering не поддерживаются.

## События и рендер

| ACP | Общий контракт хаба |
|---|---|
| Успешное открытие/загрузка | `SessionStarted(SessionId)` |
| `agent_message_chunk` с текстом текущей сессии | Накопление, затем `AssistantText` перед инструментом и в конце хода |
| `tool_call` | `ToolCall { tool: kind или "tool", summary: title или "Hermes tool" }`; строки ограничены |
| `end_turn` | `Finished { session, usage: Usage::Hermes { tokens }, background: 0 }` |
| `cancelled` | Без `Finished`; локальная отмена отображается существующим механизмом `/stop` |
| Иной stop reason / ошибка | `Failed` с ограниченным текстом причины |
| Чужая сессия, мысли, результаты инструментов, планы, оценочный usage | Не публикуются как текст ответа |

Накопленный текст ограничен 8 МиБ. Токены берутся только из `usage.totalTokens` результата prompt; отсутствие значения сохраняется как `None`. Оценочное заполнение контекста из `usage_update` не подменяет это значение.

`hub-telegram::session` использует существующие `Sender::markdown`, рендер вызовов инструментов и `format_finished`. Ответы проходят общий Markdown → Telegram HTML конвейер с экранированием, преобразованием таблиц и разбиением по лимиту; отдельного Hermes-рендера нет. Отправка идёт блоками, не потоковым редактированием сообщения.

**Известная неточность текущего отображения:** общий `format_finished` подписывает Hermes usage как «токенов в сессии», хотя источником является результат prompt. Это не подтверждённая накопленная сумма; замена подписи на «токенов за ход» в текущую реализацию не включена.

## Разрешения, вопросы и файлы

- `session/request_permission` принимается только для открытой сессии. Требуются `toolCallId` и уникальные непустые option IDs с предложенными `allow_once` и `reject_once`.
- `UserChannel::request` возвращает выбор только из предложенных разовых вариантов. Постоянные разрешения не выбираются; неверные формы отклоняются.
- Ожидание пользователя ограничено 5 минутами на уровне адаптера; тайм-аут выбирает разовый отказ. Отмена имеет приоритет над готовым разрешением, закрытый gate не одобряет поздние запросы.
- `McpHttpServer::start_with_questions` включает `send_file` и `ask_user` через общие схемы, парсеры и `UserChannel`. Обычный `start` остаётся send-file-only, сохраняя контракт Qwen.
- Сервер слушает только loopback, использует отдельный bearer token на сессию и сохраняет проверки `Host`/`Origin`. Неверные или отклонённые вызовы возвращают ошибки инструмента.
- Вопросы ограничены пятью за вызов и четырьмя вариантами каждый. Native `clarify` не является каналом вопросов пользователя в этой интеграции.
- Файлы доставляет существующий `TelegramChannel`; ограничения путей и размера остаются в транспортном слое. MCP-сервер живёт до остановки ACP-процесса.

## Доменные и пользовательские контракты

- `BackendKind::Hermes`, каноническое имя `hermes`, включён в `ALL`.
- `Usage::Hermes { tokens: Option<u64> }`.
- `HermesSettings { cli: Option<PathBuf>, profile: Option<String>, model: Option<String> }`; поля формы — строки, ошибки — `Field::Hermes(HermesField::{Cli, Profile, Model})`.
- `[hermes]` в `settings.toml` содержит только `cli`, `profile`, `model`. Старые настройки без секции читаются с defaults; новые поля для секретов не вводятся.
- Состояние темы сохраняет `backend: hermes` в существующем формате версии 1.
- `/new hermes <путь>`, `/backend hermes` и Hermes как агент по умолчанию используют существующую маршрутизацию. Переключение сбрасывает контекст, а не переносит его между агентами.
- GUI показывает CLI, профиль, модель и статус «собственная настройка Hermes (вход не проверен)». Отсутствие необязательного Hermes не блокирует запуск другого агента; недоступность выбранного по умолчанию блокирует запуск бота.

## Проверка и критерии приёмки

Детерминированные тесты покрывают новые и восстановленные сессии, подавление replay, порядок текста/инструментов, usage, последовательную очередь, сохранение inbox, EOF, отмену во время открытия и хода, разрешения, MCP-вопросы/файлы и ограниченные CLI-проверки. Core/app/Telegram тесты покрывают команды, совместимость настроек/тем, GUI и обязательность выбранного агента.

Интеграционные gates: `cargo fmt --all --check`, `cargo test --workspace --locked`, `cargo clippy --workspace --all-targets --locked -- -D warnings`, `cargo build -p hub-app --locked`, `git diff --check`.

В проверенном состоянии на macOS прошли 822 теста; 5 существующих платных live-тестов пропущены. ACP dependency check прошёл. Запуск бота сам по себе не доказывает успешную inference-сессию или доставку всех типов сообщений. Реальный прогон выполняет пользователь; успешный end-to-end результат и выполнение на Windows/Linux этой спецификацией не заявляются.

Вне объёма: общий ACP framework, перенос контекста между агентами, фоновое выполнение после завершения хода, live-steering, управление входом/ключами/установкой Hermes из хаба и автоматическое подтверждение опасных действий.
